### 2.1 认证判定顺序（L480-513）

1. 有 `Authorization: Bearer` 时优先用 Bearer；仅在完全没有 Authorization 头时才回退 Cookie `cv_token`（L460-465、L480-489）。
2. 验签、检查 `exp`、检查 `revokedJti`。
3. 读取 `users.json`：用户必须存在且 `status==='active'`；payload 的 `tv` 必须等于当前 `tokenVersion`（角色变更、改密后旧 token 立即失效）。
4. `idleTimeoutSeconds>0` 时用 `lastSeenAt`（无记录以 `payload.iat` 起算）判断空闲超时，超时写 revokedJti 并返回 `idleExpired`。

**结论**：会话/角色/停用/改密的即时失效链路完整；唯一缺口是“登出/空闲吊销不持久化”（P1-2）与 XFF 可伪造（P1-1）。

`requireRole` 在 server.js 中出现 14 次，覆盖全部写端点与管理端点；未见漏加权限的写接口。**契约矩阵与实现一致**，唯一出入是 POST /api/audit 的白名单（契约未写，见 P2-3）。

### 3.2 bootstrap 与管理员保护

- L392-444：`CV_USER` 默认 `admin`；`users.json` 为空时用 `CV_PASS` 建立首个 admin（`'已创建首个管理员账号：'`）；`CV_PASS` 为空且 `config.passHash` 也为空时打印“首次启动必须设置环境变量 CV_PASS……”并 `process.exit(1)`——与 §11.2 一致。
- 老数据目录：存在 `config.passHash/salt` 时从 config 回填 admin，此时 `CV_PASS` 允许为空（升级路径）。契约“必须非空”应注明**仅首次全新部署**（P3）。
- 最后一个 active admin：`role`（L1513-1523）与 `status`（L1525-1539）两处均拦截并返回 400“至少保留一个可用的管理员账号”；另禁止停用当前登录账号（L1525-1539）。
- 无删除端点，契约也未定义——一致。

### 3.3 注册与限流

- 用户名 `^[A-Za-z0-9_-]{3,32}$`，密码≥6，同名 pending 409 / 其他 409，`makeUserRecord` 固定 role=viewer、status=pending，写 `user_register` 审计，返回 `{ok,status:'pending',message}`——与 §11.3 一致。
- 限流：`checkRegisterRate`（L589-602）按 `clientIp` 10 分钟窗口计数，≥5 次返回 429 `bad_request`“注册过于频繁，请稍后再试”。Map 为进程内，重启清零。
- **风险**：`clientIp`（L453-457）无条件取 `x-forwarded-for` 首段；攻击者可伪造该头绕过 5 次限制，审计里的 IP 也可伪造（P1-1）。

### 3.4 令牌吊销

| 场景 | 机制 | 是否即时生效 | 是否跨重启 |
| --- | --- | --- | --- |
| 管理员停用账号 | 每次请求查 users.json 的 status | ✅ | ✅ |
| 改角色 | 每次请求用 users.json 的 role（忽略 token 内 role） | ✅ | ✅ |
| 重置密码 | `tokenVersion++`，`tv` 不等即失效 | ✅ | ✅ |
| 退出登录 | `revokedJti`（内存 Set） | ✅ | ❌ 重启后旧 token 在 exp 前仍可用（P1-2） |
| 空闲超时 | `lastSeenAt`（内存 Map）+ revokedJti | ✅ | ❌ 重启后计时归零（P2-9） |

**P0 判定**：所有客户端调用点的路径、方法、请求体字段、响应形状均能对上；未发现会导致网页登录、台账读写、图片上传、导出或管理员页面失败的契约级不一致。故本次评审 **P0 = 0**。

## 6. 契约文档自身问题（会直接误导 QA/前端）

1. **§4 #8 与 #30 重复**：同一 `GET /api/audit` 出现两次，一处说 200 条、一处说普通账号 50 条，§12 又说保留 5000 条；实现是“默认返回 200、保留 5000、普通账号 50”。（P1-4）
2. **端点总数 30 vs 实际 29**：因重复行导致，§4 自称“30 个端点”会误导验收清单。（P1-4）
3. **§8 验收写“api-smoke 覆盖全部 18 个端点”**：与 §4 的 30 行/29 个唯一端点均不符，需改为实际清单或明确“18 个核心端点”。（P1-5）
4. **§3 L45 免认证清单缺 register/register-status**：实现免认证，§4 #22/#23 也写“免认证”，只有 §3 漏列。（P1-3）
5. **§4 #2 login 的 role 只写 `admin|viewer`**：漏掉 editor，与 §11.1 三角色矩阵矛盾。（P1-6）
6. **§12 L191 称服务端自记 record_import**：服务端无法区分导入，实际不记；建议改为“record_import/record_export 由客户端上报”。（P2-7）

## 7. 缺陷分级汇总

### P0（会导前端或 E2E 失败，必须立刻修）

**无。** 本次静态复核未发现 P0。若 QA 的 E2E 用例依赖 §4 #8/#9 的“200 条”或 §8 的“18 个端点”，属于文档错误而非实现缺陷，按 P1 修文档即可。

### P1（安全/生命周期风险，或会让 QA 判错实现的文档矛盾）

1. **[安全] 无条件信任 X-Forwarded-For**：`clientIp`（L453-457）先取 XFF 首段，导致注册 5 次/10 分钟限流可被任意绕过，审计 IP 可伪造。修法：新增 `CV_TRUST_PROXY`（默认 false），仅在为 true 时信任 XFF，否则用 `socket.remoteAddress`；同时建议对 login 增加失败限速。
2. **[安全/生命周期] token 吊销不持久化**：`revokedJti`、`lastSeenAt` 均为进程内（L449-451）。重启后已登出的 Bearer 在 exp 前仍可用，空闲超时也会归零。修法：把吊销 jti 落到 `data/revoked.json`（启动加载、按 exp 清理），或 logout 时 `tokenVersion++`（代价是该账号多设备一起下线，需产品确认）。
3. **[文档] §3 L45 免认证清单补 `/api/register`、`/api/register/status`。**
4. **[文档] §4 删除 #8/#30 重复行**，合并为一条 `GET /api/audit`，写清：默认 200、`limit` 上限 5000、普通账号固定最近 50 条；并修正“30 个端点”的计数表述（唯一 29 个）。
5. **[文档] §8 “覆盖全部 18 个端点”** 与 §4 对齐（建议直接列出 29 个唯一端点，或明确 smoke 只覆盖 18 个核心端点）。
6. **[文档] §4 #2 login 的 role 改为 `admin|editor|viewer`**，并补 403 三态（pending/rejected/disabled）与响应字段。

### P2（实现与契约措辞不一致，需写回文档或小改实现）

1. **records PUT 的 If-Match 语义**：契约暗示必填乐观锁，实现缺失即强写，且忽略 body.updatedAt（L1087-1114）。建议契约写明“If-Match 可选，缺失表示强制覆盖”，并补 `count/added/removed/changed` 返回字段。
2. **settings 的合并语义**：契约写“原文/整体覆盖”，实现是默认值合并 + 强制 `version:1`（L1116-1132）。建议实现保持（对前端更稳），契约改写。
3. **POST /api/audit 白名单**：editor 也被限制为 3 个客户端动作（L1168-1188），与契约“客户端可额外 POST”不符；且 #9 的“裁剪 200”应为 5000。建议契约列出 3 个允许动作，或实现放开为“允许任意 19 项但仅记录自己”。
4. **§4 #19 `user` 字段类型未定义**：实现为 publicUser 对象（L1048-1061），建议契约列出对象字段。
5. **session/extend 审计记成 `login`**（L1063-1078）：动作语义不准，建议新增 `session_extend` 到 §12 集合，或契约注明复用 login。
6. **backup reason 中文被清洗**：`reason.replace(/[^A-Za-z0-9_-]+/g,'-')` 使中文 reason 变 `manual`（L1307-1345），与 §2 备份文件名示例 `<reason>` 的预期不符。建议支持 URL 编码/白名单中文，或契约注明仅 ASCII。
7. **导入/导出审计缺口**：服务端不记 record_import（无法区分），客户端 server 模式又不 POST audit（app.js L1450-1459 的 `state.mode==='fs'` 守卫），导致 server 模式导出/导入完全没有审计。建议前端在 server 模式也上报 record_export/record_import（这两个动作已在白名单内）。
8. **请求体/上传阈值未写入契约**：2MB JSON、32MB records、80MB 上传请求、单张 8MB、每记录 8 张，只有部分出现在 §4；建议集中到 §3 或各端点行。
9. **idleTimeout 依赖进程内 lastSeenAt**：重启后空闲计时归零（L480-513），与“空闲超时强制下线”的安全预期有差距；可与 P1-2 一并持久化，或契约注明“空闲计时仅在进程生命周期内有效”。

### P3（可选优化/加固）

- CORS 对任意 Origin 回显并允许凭证（L640-653）；仅内网/反代场景可接受，公网暴露应加白名单。
- `revokedJti` 只增不减，无按 exp 清理，长时间运行内存缓慢增长。
- `apiHealth` 每次请求遍历 images 目录统计（L965-975），记录/截图多时有 IO 开销。
- 上传不校验 recordId 是否存在于台账（L1193-1251），可产生孤儿图片目录。
- 静态文件拒绝点开头路径（L848-850），`.well-known` 的 ACME HTTP-01 校验会 404；证书建议都在反代层申请。
- `CV_PORT` 非数字未校验，直到 listen 才报错。
- TTL 最小 60 秒、token 额外 `n/tv`、`.lock` 额外 `ts/id` 均未写入契约。
